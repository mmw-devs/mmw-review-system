# 攻略审核平台：平台介绍与字段说明

本文说明 `mmw-review-system` 的用途、初版工作流程和攻略文件的字段设计。

**状态：平台目标设计，命令行转换部分已实现。** 当前可以读取文档、转换并在本地保存 JSON 和图片；审核页面、人工通过／驳回流程、组织身份校验和网站渲染尚未实现。当前操作以[命令行说明](converter-cli.md)为准，本文第 1、2 节描述未来完整平台的工作方式。字段契约见 [0.1.0 JSON 结构](strategy-json-format.md)及配套 Schema。

## 1. 平台简介

这是一个供 MMW 攻略组飞书组织内部人员使用的攻略审核平台。

作者在飞书中撰写攻略。审核人员在平台提交目标文档链接，平台读取文档并提供审核内容。审核人员人工决定通过或驳回；通过后，平台将攻略转换成统一格式的文件，保存到服务器本地。

攻略作者负责机制和解法的内容；审核人员负责内容是否可以接纳；平台负责获取、转换、保存和反馈结果。字段校验不能代替人工判断攻略是否正确。

```text
作者 → 飞书攻略文档
             ↓ 读取
审核人员 → 审核页面 → 人工通过／驳回
                          ↓ 通过
                    转换并检查结果
                          ↓
                    服务器本地文件
```

初版审核整份文档，只审核、不在审核页面编辑正文；修改回飞书完成。不选择章节或区域，不加入 AI 辅助，也不自动发布到网站。后续考虑按阶段分别审核，以及复用已经审核的部分。

攻略内容统一导出为 JSON，用 JSON Schema 检查结构，再由网页渲染程序生成页面。初版不额外导出 Markdown 或 HTML；现有网站仍需增加读取该格式的适配逻辑。图片等资源可与 JSON 一同保存，不属于另一种攻略内容格式。

## 2. 审核人员如何完成一次审核（目标流程）

| 环节 | 人员操作 | 平台的预期行为 |
| --- | --- | --- |
| 发起审核 | 提交飞书文档链接 | 检查访问权限，读取全文，反馈获取结果 |
| 查看内容 | 阅读本次获取的攻略 | 展示文字、图片及可支持的格式；说明未读取或无法展示的内容 |
| 人工决定 | 通过或驳回，可填写意见 | 保存审核结果；驳回时不生成通过审核的产物 |
| 转换预检 | 查看不支持转换的内容清单 | 时间轴组件、视频及其他无法处理的内容均列出位置与原因；没有这些内容则正常继续 |
| 选择处理 | 选择丢弃清单内内容继续转换，或放弃本次转换 | 不默认丢弃；选择仅对本次快照和所列内容生效 |
| 格式转换 | 审核通过且转换选择已明确后由系统执行 | 仅转换允许保留的内容，检查字段和引用；发现新问题重新提示 |
| 保存结果 | 查看任务结果 | 将产物保存到服务器本地，明确显示成功、部分完成或失败 |

建议审核和转换使用同一次获取的文档内容。飞书原文后续修改，不应自动替换正在审核的内容；重新获取应形成新的审核版本。具体版本保存方式属于系统内部设计。

人工审核通过和文件转换成功分别记录。时间轴组件、视频及其他当前无法处理的内容必须列出位置与原因，由审核人员选择“丢弃清单内内容，只转换其他内容”或“放弃本次 JSON 转换”。未选择时不生成最终 JSON。主动丢弃后的结果标为“已转换，按确认清单排除部分内容”，不能称为完整保留全文。放弃转换不改变已经作出的人工审核结论，也不改动飞书原文。

后续读取层拟改为直接调用飞书官方 API，以 H5 授权的用户身份读取文档；接口权限、原文访问权限和系统审核角色分别校验。模块划分、快照兼容、账号及任务权限见[飞书 API 读取与基础权限方案](feishu-api-and-permissions.md)。该方案尚未实现，当前 CLI 用法不变；角色和任务范围的建议默认仍需在实施前确认。

## 3. 攻略内容如何划分

攻略文件只描述三部分内容：副本数据、阶段与机制定位、机制与解法正文。

| 部分 | 回答的问题 | 内容 |
| --- | --- | --- |
| 副本数据 | 这是哪个副本的攻略？开始阅读前需要知道什么？ | 名称、简介、封面、视频、攻略须知、战前准备 |
| 阶段与机制定位 | 有哪些阶段和机制？点击目录跳到哪里？ | 阶段名称、机制名称、标识和跳转地址 |
| 机制、解法与说明 | 机制是什么？玩家怎么处理？有哪些提醒？ | 按原文顺序编排的标题、机制说明、解法、备注及普通内容 |

### 3.1 目录和正文的关系

目录项只负责显示名称和跳转。正文保存实际的说明、图片和解法，两者通过标识关联。

例如，目录项“无之膨胀”的标识是 `void-expansion`，正文中对应机制标题的标识也为 `void-expansion`。点击目录时跳到这个标题，读者继续向下阅读机制说明和解法。

正文不放进导航的 `mechanics[]`，也不在目录中重复保存。

### 3.2 建议的 JSON 组织方式

为明确三部分的存放位置，建议使用 `duty`、`phases` 和 `phase_contents` 三个业务顶层字段，另以 `schema_version` 标识文件格式版本。它们是本平台建议的文件结构，不是现有网站已提供的导入接口。

```text
攻略
├─ schema_version：格式版本，例如 0.1.0
├─ duty：副本数据
│  ├─ id、name、short、type 等基本信息
│  ├─ introduction：攻略须知正文
│  └─ preparation：战前准备正文
├─ phases[]：阶段与机制目录
│  ├─ id、title、subtitle、name、base、href
│  └─ mechanics[]：机制定位
│     └─ id、name、name_en、name_ja、name_ch、href
└─ phase_contents[]：各阶段正文
   ├─ phase_id：对应 phases[].id
   └─ sections[]：按阅读顺序排列的区块
      ├─ 标题、机制说明、解法、说明、普通内容
      ├─ 多解法：solutions[]
      └─ 折叠内容：summary、details
```

同一阶段内可以按“机制标题 → 机制说明 → 解法 → 注意事项 → 下一个机制标题”的顺序排列。复杂机制中的小标题和补充段落使用普通内容区块，不要求额外建立子机制对象。

审核人员、审核状态、来源快照和转换日志由系统单独保存，不属于攻略内容字段。

## 4. 副本数据字段

以下路径相对于 `duty`。“必填”是本设计对完整结构化产物的建议，不表示飞书原文一定提供了对应信息。无法识别的必填值应提示补充，不能猜测生成。

| 字段 | 类型 | 用途与要求 |
| --- | --- | --- |
| `id` | string | 必填，副本短标识，例如 `m5s`；不含游戏版本目录或斜杠，不直接作为任意本地文件路径 |
| `name` | string | 必填，副本全名 |
| `short` | string | 副本简称，可选 |
| `type` | string | 保留实际副本的业务分类，可选；不依赖网站已有同名字段。具体分类枚举和必填时机仍待确定 |
| `title` | string | 必填，攻略页面标题 |
| `description` | string | 页面简介，可选 |
| `banner` | string | 封面图片路径或地址，可选；不自动将第一张图片认作封面 |
| `videoLink` | string | 外部攻略视频的普通链接，可选，不含视频文件／播放器；不自动用此字段替代被排除的视频块 |
| `introduction` | Body | 攻略须知正文，可选 |
| `preparation` | Body | 战前准备正文，可选；包括开放条件、标点、默认站位等 |

`id: "m5s"` 对应网站路径 `/07/m5s`，其中 `07` 为游戏版本目录，由网站侧维护。本攻略格式不增加游戏版本号或副本页面路径字段。网站内部 `dutyId` 的映射属于接入层。

`Body` 表示可以包含图文和格式的正文，见第 7 节。多段准备内容可以在同一正文中保留小标题和原有顺序。

网站的导航分组、发布日期、上线状态等由网站接入流程处理，不要求从攻略原文提取。审核通过不等于已发布。

## 5. 阶段与机制定位字段

### 5.1 阶段

以下路径相对于 `phases[]`。

| 字段 | 类型 | 用途与要求 |
| --- | --- | --- |
| `id` | string | 必填，攻略内唯一的阶段标识，例如 `p1`；不随显示标题修改而变化 |
| `title` | string | 必填，阶段标题，例如 `Phase 1` 或 `P1阶段` |
| `subtitle` | string | 阶段副标题，可选，例如“小世界” |
| `name` | string | 必填，导航显示名称，例如“P1 - 小世界” |
| `base` | string | 阶段时间起点，可选；建议统一为 `MM:SS` 或 `MM:SS.sss`，表示相对整场战斗的起点。未知时省略，不填零代替未知 |
| `href` | string | 阶段页面地址，可选；接入网站时生成 |
| `mechanics` | array | 机制导航列表；尚未识别机制时可为空，并报告待确认项 |

阶段按原文顺序保存，不依据标题数字自动重排。暂不套用旧项目的阶段编号范围、半阶段规则和标题字符限制。

### 5.2 机制目录项

以下路径相对于 `phases[].mechanics[]`。

| 字段 | 类型 | 用途与要求 |
| --- | --- | --- |
| `id` | string | 必填，对应本阶段正文中的机制标题 `sections[].id` |
| `name` | string | 必填，机制导航显示名称 |
| `name_en` | string | 英文名称，可选 |
| `name_ja` | string | 日文名称，可选 |
| `name_ch` | string | 中文名称，可选；含义沿用目标网站约定 |
| `href` | string | 跳转位置，可由 `id` 生成，例如 `#void-expansion` |

同名机制可以多次出现，但必须有不同定位 ID。不能只凭名称把不同时间出现的机制合并。多语言名称缺失时省略，不自动翻译补全。

## 6. 机制、解法与说明字段

### 6.1 阶段正文

| 字段 | 类型 | 用途与要求 |
| --- | --- | --- |
| `phase_contents[].phase_id` | string | 必填，引用已有的 `phases[].id`；每个阶段恰好对应一份阶段正文 |
| `phase_contents[].sections` | array | 必填，按阅读顺序排列的正文区块 |

### 6.2 区块类型

| `sections[].type` | 用途 | 使用的主要字段 |
| --- | --- | --- |
| `separator` | 机制标题或分隔标题 | `id`、`title` |
| `mechanic` | 解释机制规则 | `title`、`content` |
| `solution` | 一套解法 | `title`、`content`、可选 `beta` |
| `multi_solution` | 同一处的多套备选解法 | `title`、`solutions`、可选 `defaultSolution` |
| `note` | 说明、风险、职能提示 | `title`、`content`、可选 `roles` |
| `collapse` | 可折叠的补充说明 | 可选 `title`、`summary`、`details` |
| `content` | 普通正文、小标题、尚未明确分类的内容 | 可选 `title`、`content` |

这些类型对应网站已有组件的用途，但上述 JSON `type` 值是本平台的建议，不是网站组件现有属性。

### 6.3 区块字段

以下路径相对于 `sections[]`。按区块类型使用相关字段，不要求每个区块包含所有字段。

| 字段 | 类型 | 用途与要求 |
| --- | --- | --- |
| `id` | string | 必填，本阶段内唯一的正文定位标识，与解法锚点共同检查唯一性 |
| `type` | enum | 必填，取值见 6.2 |
| `title` | string | 区块标题；机制定位标题必填，其余按原文保留，允许没有标题 |
| `content` | Body | 机制、单解法、说明或普通内容的实际正文 |
| `roles` | array | 职能提示适用对象，可选；建议取值 `tank`、`healer`、`dps`。未填表示未作职能限定 |
| `beta` | boolean | 解法是否明确标为 Beta，可选；`false` 或缺失均不证明已经实战验证 |
| `solutions` | array | 多解法区块专用，包含各套解法；至少一项 |
| `defaultSolution` | string | 默认展示的解法 ID，可选；必须引用本区块的一套解法，由人工指定 |
| `summary` | Body | 折叠区块专用，收起时的摘要 |
| `details` | Body | 折叠区块专用，展开后的详细正文 |

`multi_solution` 使用 `solutions` 保存正文；`collapse` 使用 `summary` 和 `details`。不再把同一份正文重复存入它们的 `content`。

没有指定 `defaultSolution` 时，不自动将第一套解法标成推荐方案。页面初始如何展示属于后续展示规则。

### 6.4 每套解法

以下路径相对于 `sections[].solutions[]`。

| 字段 | 类型 | 用途与要求 |
| --- | --- | --- |
| `id` | string | 必填，解法定位标识；修改解法标题时保持不变 |
| `title` | string | 必填，例如“黑洞基准”“BOSS基准” |
| `content` | Body | 必填，解法的图文正文 |
| `beta` | boolean | 是否明确标为 Beta，可选，含义同 6.3 |

## 7. 正文需要保留什么

正文用于保存作者实际写下的内容。机制说明、解法、备注、攻略须知和战前准备共用同一种正文格式。

| 内容 | 需要保留的信息 |
| --- | --- |
| 文字 | 文字顺序、段落、换行、加粗、斜体、下划线、删除线、文字颜色 |
| 标题与列表 | 小标题、标题级别、有序／无序列表及嵌套关系 |
| 图片 | 图片引用、原有位置、原文图注；不把自动图片描述当作作者图注 |
| 链接 | 链接文字与目标地址 |
| 表格 | 单元格内容、行列关系、合并关系 |
| 分栏 | 各列的内容与顺序，保留图文之间的对应关系 |
| 提示框 | 图标、文字、背景和边框样式 |
| 代码块 | 游戏宏、战术板代码等原文，保留空格和换行 |

`Body` 使用有顺序的内容块数组；段落和标题中包含文字及换行节点，表格、分栏等容器包含嵌套正文。具体节点、样式和字段约束见 [JSON 结构说明](strategy-json-format.md)及 [JSON Schema](../schemas/strategy.schema.json)。它们是待实际转换与展示验证的设计，不直接套用旧项目的富文本结构。

伤害、状态效果、目标选择、站位优先级、成功失败条件和文字时间轴，初版保存在正文中，不要求进一步抽取为独立业务字段。

飞书嵌入电子表格需要补取，失败时进入不支持转换清单。时间轴组件、其他第三方组件、嵌入网页、视频、音频及附件块初版不转换。画板、复杂数据视图、裁剪图片与同步块的条件支持规则见[转换规则](feishu-authoring-and-conversion.md#6-不支持内容的选择流程)。占位和原始数据只保留在审核预检与内部快照，最终攻略 JSON 不输出占位。普通文字时间轴仍按正文处理；战术板代码不等于交互脚本。

审核页区分两类提示：“无法转换，需要选择丢弃或取消”与“可转换，展示效果需检查”。仅外观变化不自动丢弃内容；不能保留攻略含义时才进入不支持清单。评论、编辑历史等协作记录默认不导出，无需逐次确认。提示、排除清单和选择记录保存在内部任务中，不加入攻略 JSON。

## 8. 现有攻略的转换规则与边界

### 8.1 标题和内容归类

现有文档的标题级别不统一，不能仅凭“一级标题”“七级标题”判断其业务用途。应结合“P1阶段”“解法”等文字和上下文识别，并保留原文顺序。

分类不明确的区块先使用 `content` 保存，不删除，不强行归入附近机制。如果连所属阶段都无法确定，应保留获取的原文并提示待确认；在归属解决前，不宣称已经生成完整的结构化产物。初版不在审核页改写正文；需由作者修正飞书文档或明确转换映射，具体提示方式待设计。

初版建议使用一级标题表示阶段、二级标题表示机制、三级标题表示机制说明／解法／注意事项。旧文档可依据明确文字兼容识别，不要求先批量改写；具体规则及疏漏处理见[飞书攻略撰写规范与 JSON 转换规则](feishu-authoring-and-conversion.md)。

### 8.2 全文范围

初版不提供按 P1、P2 分别审核，也不提供任意区域选择。系统先检查本次读取的全文；只有识别出的不支持转换内容可在审核人员明确确认后排除，其余内容按全文转换。

原文中的 Beta、删除线、未填写的模板内容和草稿说明应保留，不能因审核通过就自动改写成正式结论。飞书批注作为审核参考单独处理，不自动混入攻略正文；是否读取、如何展示批注仍待确定。

### 8.3 文件与资源

平台目标是将产物保存到服务器本地。当前命令行版本保存在运行机器的 `data/runs/conversion-<RUN_ID>/`，正式文件为 `strategy.json`，图片使用 `assets/` 相对路径；也可指定其他任务父目录。目录内还有内部快照、报告和中间文件，详见[输出文件说明](converter-cli.md#3-输出目录和文件用途)。网站渲染与部署仍需实现；文件齐全不等于已经具备网页预览。

普通文档表格按正文转换，简单嵌入电子表格通过额外读取转换，未适配结构进入不支持清单。时间轴组件即使可读也不转换。历史调查与当前实现的验证范围不同；当前能力见[命令行说明](converter-cli.md#5-支持范围与已知限制)，资源契约见 [JSON 结构说明第 5 节](strategy-json-format.md#5-资源与渲染边界)。
