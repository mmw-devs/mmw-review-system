# 攻略 JSON 结构：0.1.0 设计稿

本文件将[平台与字段说明](strategy-review-platform.md)落实为具体 JSON 结构。初版只做人工审核，正文修改回飞书完成；此格式保存攻略内容，不包含编辑器历史、审核记录和获取日志。JSON 是内部转换、校验和审核预览的中间格式；新任务正式导出攻略站使用的 `.astro` 页面及资源，由攻略站构建为 HTML。

**这是初版契约。H5 已接入转换与审核预览，当前支持范围见[服务运行说明](review-server.md)。** Astro 输出映射见[攻略站格式白名单](feishu-authoring-and-conversion.md#22-攻略站实际格式与组件白名单)；网站路由、完整副本目录配置及发布仍由网站侧处理。

- [简短示例：恩欧·无之膨胀](examples/enou-strategy.v0.1.json)：先阅读这份，理解目录与正文。
- [全字段示例](examples/strategy-all-fields.v0.1.json)：包含所有可选字段和正文类型；补充内容与资源均为演示。
- [JSON Schema](../schemas/strategy.schema.json)：使用 JSON Schema Draft 2020-12，检查字段和类型。

## 1. 文件长什么样

```json
{
  "schema_version": "0.1.0",
  "duty": {
    "id": "demo-enou",
    "name": "恩欧歼殛战",
    "title": "恩欧歼殛战攻略"
  },
  "phases": [
    {
      "id": "p1",
      "title": "P1阶段",
      "name": "P1",
      "mechanics": [
        { "id": "void-expansion", "name": "无之膨胀" }
      ]
    }
  ],
  "phase_contents": [
    {
      "phase_id": "p1",
      "sections": [
        {
          "id": "void-expansion",
          "type": "separator",
          "title": "无之膨胀"
        },
        {
          "id": "void-expansion-description",
          "type": "mechanic",
          "content": [
            {
              "type": "paragraph",
              "content": [
                { "type": "text", "text": "黑洞释放钢铁或月环AOE。" }
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

`phases[].mechanics` 只提供目录；`phase_contents[].sections` 保存正文。上述两个 `void-expansion` 指向同一个机制标题。

## 2. 文件与字段规则

| 项目 | 约定 |
| --- | --- |
| 格式版本 | `schema_version` 必填，当前固定 `0.1.0` |
| 三个业务部分 | `duty`、`phases`、`phase_contents` 都必填 |
| 可选字段 | 未知或不适用时省略，不填 `null` 或空字符串代替未知 |
| 普通名称与标题 | 允许中文、空格和标点，不能全部为空白 |
| 正文文字与代码 | 保留空格、换行；不统一 trim。空段落用 `content: []` 表示 |
| 标识 | 阶段、区块和解法 ID 使用小写英文字母、数字、短横线、下划线；由系统生成或映射，不依赖显示名称唯一 |
| 副本标识 | `duty.id` 为不含斜杠的副本短标识，例如 `m5s`；不作为文件系统路径直接使用 |
| 游戏版本与地址 | `/07/m5s` 的 `07` 为游戏版本目录，由网站侧维护；攻略转换不增加版本号或副本页面路径字段。现有可选阶段 `href` 仅供网站接入时生成，转换时可省略 |
| 未知字段 | Schema 拒绝未定义字段；新增结构应更新契约，不悄悄写入自定义字段 |
| 阅读顺序 | 以数组顺序为准，不按名称、ID 或标题数字重新排序 |
| 类型范围 | 保留 `duty.type` 作为实际副本的业务分类；暂为可选非空字符串，具体枚举与必填时机待确定，不依赖网站已有分类字段 |

未识别出阶段时，不伪造 P1。系统保留原始快照并报告结构化失败，直到作者修正飞书文档或明确转换映射。

## 3. 各类区块怎样写

所有 `sections[]` 都有 `id`、`type`，其余字段按类型使用。

| `type` | 必填内容 | 可选内容 |
| --- | --- | --- |
| `separator` | `title` | 无 |
| `mechanic` | `content` | `title` |
| `solution` | `content` | `title`、`beta` |
| `multi_solution` | `solutions`，至少一项 | `title`、`defaultSolution` |
| `note` | `content` | `title`、`roles` |
| `collapse` | `summary`、`details` | `title` |
| `content` | `content` | `title` |

每个 `solutions[]` 条目必须有 `id`、`title`、`content`，可选 `beta`。

- `roles` 只用于 `note`，填写 `tank`、`healer`、`dps` 中的一项或多项，不重复。
- `beta` 只用于单解法或多解法中的具体方案。`true` 表示明确标注 Beta；实战验证状态需另行核对。
- `defaultSolution` 必须指向当前区块的某套解法。没有人工指定时省略，不推断首项是推荐解法。
- `multi_solution` 不允许再写 `content`；`collapse` 不允许再写 `content` 或 `solutions`，避免同一正文存在多个副本。

一个阶段的 `sections` 至少有一项。正文先后关系不依赖机制目录：没有导航条目的普通说明也可以正常出现。

## 4. 正文 Body 的具体格式

`Body` 是有顺序的内容块数组，至少一项。它用于 `introduction`、`preparation`、区块 `content`、解法 `content`、折叠 `summary/details`，也可以嵌套在列表、表格、分栏等内部。

### 4.1 段落、标题与行内文字

段落和标题的 `content` 是行内节点数组：

```json
{
  "type": "paragraph",
  "content": [
    {
      "type": "text",
      "text": "防护职能注意：",
      "style": { "bold": true, "color": "#245bdb" }
    },
    { "type": "text", "text": "T在人群后方挡枪。" },
    { "type": "hard_break" },
    { "type": "text", "text": "人群靠近BOSS。" }
  ]
}
```

| 节点／字段 | 规则 |
| --- | --- |
| `paragraph.content` | 行内节点数组，可为空以保留空段落 |
| `heading.level` | 必填，整数 1–9；保存原文级别，不直接决定阶段或解法归属 |
| `heading.content` | 行内节点数组 |
| `align` | 段落、标题可选：`left / center / right / justify` |
| `indent` | 段落、标题可选非负整数，表示缩进层级 |
| 行内 `text` | 必填 `text` 字符串，至少一个字符；可选 `style` 和 `href` |
| 行内 `hard_break` | 只有 `type`，表示显式换行 |
| `style` | 可选 `bold`、`italic`、`underline`、`strike` 布尔值，以及 `color`、`background_color`、`font_size_px` |

颜色统一保存为六位十六进制值，例如 `#245bdb`，不限定旧项目的调色板。字号是正数像素值，只在来源确实提供时写入。

`href` 支持 HTTP(S) 链接、`#锚点` 和站内 `/路径`。锚点有效性还需按第 6 节检查。暂不支持任意 HTML、CSS、JavaScript 或其他链接协议；遇到来源中无法表达的格式要报告，不能宣称无损转换。

### 4.2 图片与代码

| 类型 | 必填字段 | 可选字段 |
| --- | --- | --- |
| `image` | `src` | `alt`、`caption`、`width`、`height`、`align` |
| `code` | `text` | `language`、`wrap` |
| `divider` | 只有 `type` | 无 |

- `src` 为产物目录内的相对路径，或 HTTP(S) 地址。相对路径使用系统分配的 ASCII 文件名，例如 `assets/diagram-01.png`；不使用飞书标题拼接路径。
- `caption` 是行内节点数组，可带颜色、链接等；`alt` 为纯文本替代说明，不能自动充当图注。
- 图片尺寸为正整数像素；图片 `align` 可用 `left / center / right`。
- 当前只接收上表定义的正文节点；没有白名单映射的源组件归为必须修正，不自动降级为链接。原文已有的普通 HTTP(S) 链接及元数据 `videoLink` 仍作为链接保存，不承诺播放器、附件预览或资源获取。
- `code.text` 原样保留空格与换行；游戏宏和战术板代码用此类型保存。`language` 可写 `plain_text`。

### 4.3 列表、表格与分栏

| 类型 | 结构 | 说明 |
| --- | --- | --- |
| `list` | `ordered`、`items[]`，可选 `start` | 每个 `items[]` 元素都是 Body；允许嵌套列表。只有有序列表允许填写正整数起始序号 |
| `table` | `rows[].cells[]`，可选 `column_widths_px[]` | 行和单元格按原文顺序保存；列宽为正数像素 |
| 表格单元格 | 必填 `content`，可选 `row_span`、`col_span`、`header`、`background_color` | `content` 是 Body；省略跨度时按 1 解释，省略 `header` 时按普通单元格解释 |
| `columns` | 至少两项 `columns[]` | 每列必填 `content`（Body），可选 `width_weight` 正数；省略时按 1 解释 |

`width_weight` 表示列宽比例：`2` 和 `1` 表示约 2:1，不要求权重之和等于 1。

表格中被合并单元格覆盖的位置不再写占位单元格。解析时按行从左到右，将每个单元格放入第一个未被上方跨行单元格占用的位置。某行被上方跨行单元格完全覆盖时，允许 `cells: []`；不允许整个表格为空或出现覆盖冲突、越界和孔洞。

### 4.4 提示、引用与未展开内容

| 类型 | 必填字段 | 可选字段 |
| --- | --- | --- |
| `callout` | `content`（Body） | `icon`、`background_color`、`border_color` |
| `quote` | `content`（Body） | 无 |

`callout.icon` 是原文图标文字或 emoji；正文中的职能标签不必强制转成网站图标组件。

无法解析的源内容只保留在内部快照及必须修正清单，不向最终 JSON 写占位。按[两类问题规则](feishu-authoring-and-conversion.md#4-问题只分两类)打回原文修改，不能确认丢弃后导出。

## 5. 资源与渲染边界

### 5.1 普通表格与嵌入电子表格

普通文档表格的行、单元格和合并关系属于正文，可以转换为 `table`。嵌入电子表格则是另一个资源：前次读取两份攻略时，普通表格返回了单元格，而嵌入表格只返回引用。嵌入表格需另外读取其单元格内容。

[读取调查](investigations/2026-10-18-feishu-reading.md)已验证这两份攻略引用的表格可补取完整报告范围内的单元格值、颜色、字号和列宽。其他表格的权限、公式、筛选及复杂布局仍需验证。建议初版保存审核时可见的单元格内容与可获取样式，不复刻在线表格编辑器和公式重算；历史 CLI 曾实现简单嵌入表格补取；H5 尚未适配嵌入电子表格，当前归为必须修正。若未读取内部内容，列为必须修正并说明缺失，不在最终 JSON 中输出占位。

### 5.2 白名单外内容

源文档中的组件标识或只读占位用于定位组件；转换需要可映射的正文内容。转换器仅接受有明确输出映射的类型，未适配组件一律提示“该组件无法解析”并打回原文修改。系统不维护逐项拒绝的组件黑名单；新增类型默认不能导出。普通文字、图片或普通表格形式的时间轴按其格式正常处理。

### 5.3 图片与资源

H5 会将可处理图片下载到任务目录的 `assets/`，在 JSON 中使用相对路径引用，并核对文件签名和摘要。真实攻略的显示效果仍需联调核对。未映射的源组件归为必须修正。已识别裁剪属性的图片保留完整原图并进入表现待确认，必须明确提示裁剪尚未还原；未知变换或下载失败仍为必须修正。当前目录与下载范围见[H5 存储说明](review-server.md#4-存储与恢复)。

内部 JSON 保存结构和文字，图片仍使用自身的媒体格式。Astro 导出包将本地图片放入 `public/review-assets/`，页面使用对应站内地址；不把图片编码进正文，也不附带原始快照。

正式产物中的相对资源必须真实存在于产物目录。外部资源需单独检查可访问性，并在离线使用前下载。契约允许符合约束的相对路径；当前 H5 实现固定使用 `assets/`。

结构文件不记录下载失败或审核状态。这些信息由任务记录保存，审核页面应显示。资源缺失、未展开内容和无法表达的源格式不能被静默忽略。

文字和代码必须按纯文本渲染，不作为 HTML 或脚本执行。URL 的 Schema 检查只覆盖基本格式；当前关联校验还拒绝带凭据的 HTTP(S) 链接。H5 图片通过发起人的用户授权调用飞书 API 获取，当前不提供通用外部 URL 下载器；后续扩展时需单独设计访问控制。

已知显示差异统一使用“表现待确认”，需对照原文明确确认；无法解析、资源缺失或结构错误统一使用“必须修正”。具体判定见[转换规则](feishu-authoring-and-conversion.md#4-问题只分两类)。评论、编辑历史等协作记录不进入攻略正文；两类问题、人工决定和表现确认记录保存在任务中，不增加最终 JSON 字段。

## 6. Schema 以外的关联校验

标准 JSON Schema 检查字段与类型。当前转换器还检查下列阶段、导航、默认方案、锚点和表格关系，并核对本地图片摘要；完整语义识别和跨网页路由验证仍不能自动保证：

1. `phases[].id` 全文唯一；每个阶段恰好有一份 `phase_contents`，不能引用不存在的阶段。
2. 每个阶段的区块 ID、所有多解法条目的 ID 共同唯一。不同阶段可以重复使用相同的局部锚点。
3. 当前阶段的每个机制导航 ID 必须找到一个同 ID 的 `separator`。目录项 ID 不重复；填写了 `href` 时必须等于 `#` 加该 ID。
4. `defaultSolution` 只引用所在多解法区块的方案。
5. 正文中的本页 `#锚点` 必须存在于当前阶段；跨页面链接需结合最终路由检查。攻略须知和准备正文没有阶段上下文，其 `#锚点` 在首页路由未确定前不能报告为有效。
6. 表格按第 4.3 节计算后必须形成完整矩形；跨行不超过表格总行数，单元格不重叠，列宽数量与逻辑列数一致。
7. 资源可访问性、源内容是否遗漏、文本是否仅为空段落需单独检查。未知内容必须修正，不提供排除授权；最终产物只能包含白名单内的节点。

未识别任何机制时，`mechanics: []` 在结构上合法，但按目标规则仍应报告目录尚未确认；当前实现尚未生成这一专门提示，需人工核对。Schema 用于检查文件格式；人工审核、资源完整性和网站展示分别验收。

## 7. 后续仍需决定的内容

- 副本类型的业务枚举与必填时机；游戏版本目录与副本 ID 的映射由网站侧处理。
- 补充 H5 的嵌入电子表格、复杂表格和裁剪图片等适配。后续扩展须按转换规则第 6 节同步更新白名单、适配器和渲染验证。
- 正文展示效果的实际验证，以及正式产物需要达到的完整性门槛。
- 在目标攻略站完成导出页面、目录和资源的接入与实际展示验收。

当前 H5 使用该契约生成内部候选稿，再转换为 Astro 产物；未实现的来源适配统一归为必须修正，真实飞书联调和网站接入需分别验收。
